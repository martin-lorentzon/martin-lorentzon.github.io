# Project conventions

- Avoid shadows: don't add `shadow-*` utilities, and add `shadow-none` where a daisyUI component shows one by default — but only on elements you're actively changing in the current task. A shadow elsewhere was added intentionally; leave it unless asked.
- Prefer daisyUI's own component classes (e.g. `btn`, `card`, `input`) over building the same thing from raw Tailwind utilities. Fall back to plain Tailwind only for layout/spacing or when daisyUI has no matching component.
- Repeated utility groups become semantic classes in `src/input.css` — follow the `semantic-classes` skill (reuse existing classes first, naming, color tokens). Two hard rules:
  - Semantic classes stick to the element that holds the text (`<p>`, `<ul>`, a heading), never a wrapper div. The wrapper carries only layout (`mt-*`, `space-y-*`).
  - Never `@apply` a daisyUI component class (`collapse`, `join-item`, `menu`, etc.) — its behavior lives in parent/child selectors that `@apply` drops (an FAQ item rendered permanently collapsed when tried). Keep daisyUI classes literal in the HTML.
- Escape `&` as `&amp;` in HTML text content (headings, copy, etc.) — don't leave bare ampersands.
- When adapting pasted/legacy copy, fix obvious typos and spelling errors silently rather than preserving them verbatim. Only flag a change if the intended wording is ambiguous.
- Every icon on the site comes from lucide (`<i data-lucide="...">` + `vendor/lucide.min.js`, rendered by `lucide.createIcons()`). Never hand-write or paste a raw `<svg>`/`<path>`, even for framework widgets like daisyUI's theme swap, and convert legacy markup from other icon sets (e.g. Material Symbols) to the closest lucide equivalent. If you need a component's structural classes (e.g. `swap-off`/`swap-on`) on the icon, put them on the `<i>` — they carry over to the rendered `<svg>`.
- Site copy is Swedish (`<html lang="sv">`). Use `&ndash;` for ranges (`2022&ndash;2024`). Plain hyphens are fine in body-copy compounds (`3D-vyn`); the non-breaking hyphen rule below is for headings and short text.
- Gradient text colors (`bg-linear-to-r from-* to-*`) are picked per section to fit that section's content — there's no fixed palette to cycle through. Just avoid repeating the same gradient in adjacent sections.
- Avoid awkward line breaks in headings and short text, especially on mobile widths (~360-400px):
  - When a heading ends with a trailing icon (`<i data-lucide="...">`), don't lay it out as a separate flex item alongside the text (`flex flex-wrap items-center gap-3`) — on narrow screens the icon gets orphaned onto its own line below the wrapped text. Instead wrap the icon and the word it follows together in `<span class="whitespace-nowrap">last-word<i ...></i></span>` (`ml-2`/`ml-3` on the icon for spacing) so it always travels with that word.
  - For a hyphenated compound that should read as one unit (e.g. "in-house-verktyg", "e-post"), use a non-breaking hyphen (`&#8209;`) instead of a plain `-`. It renders identically but stops the browser from splitting the word at the hyphen, so a wrap moves the whole compound to the next line instead of stranding a fragment like "in-" or "e-".
  - For long unbreakable strings like an email address, don't rely on `break-words`/`overflow-wrap` alone — it can strand a single character (e.g. a lone "e" off "martinlorentzon.se"). Add explicit `<wbr />` at natural boundaries instead (e.g. `contact@<wbr />martinlorentzon<wbr />.se`).
- This is a static-build project (`npm run build`, Tailwind CLI → `dist/output.css`) — after adding a Tailwind class that isn't already used elsewhere in the file, rebuild before checking in the browser, or the new class won't be in the compiled CSS and will silently have no effect.
- Mark every top-level structural region of `index.html` with a boxed banner comment, and add one whenever a new top-level region is introduced (don't wait to be asked). The banner is one multi-line comment with a `MARK:` label, which VS Code shows as a section header in the minimap:
  ```
  <!-- ======================================================================
       MARK: SECTION NAME
       ================================================================== -->
  ```
  - Keep `MARK: label` alone on its own line, with nothing after the label. VS Code takes everything after `MARK:` to the end of the line as the minimap label, so a closing `-->` or trailing padding on that line would show up there (`HE…-->`). That's why the banner is one comment, not three separate `<!-- -->` lines.
  - "Top-level" means: header/navbar, each `<section id="...">` in `<main>`, footer, the mobile drawer menu, and the scripts block at the end of `<body>` — not nested subsections within them (e.g. the FAQ accordion or footer link columns don't get their own banner).
  - Match the indentation of the element the banner precedes, and indent the two continuation lines 5 more spaces so they line up under the first `=`. The top border has 4 more `=` than the bottom one (which carries the ` -->`), so both borders end in the same column (see existing banners in `index.html` for the pattern).
  - Name the section in caps, using the element's `id` or a short plain-English label (e.g. `HERO`, `KONTAKT`, `MOBILE MENU`). Keep names short, and never add a parenthetical (no `FOOTER (FAQ + links)`) — the name is the whole minimap label, so it should read at a glance.
